## 2026-08-12 (3) — 적대적 검증 · 라이브 실측으로 API 호출방식 확정

### 1부: 적대적 검증 (로컬 HTTP 서버 반복 호출)
접속이 막혀 있던 동안, monkeypatch 가 아니라 **진짜 로컬 HTTP 서버**를 띄워 실제 소켓·requests
세션·인코딩 감지·재시도 경로를 태우며 반복 호출했다. **검사 9,282건 중 29건 실패 → 결함 4종.**

| # | 결함 | 발견 방식 |
|---|------|-----------|
| 1 | 🔴 `resultCode` 거짓 양성 — `"00"` 이 zfill 을 거쳐 `"000"`(SYSTEM ERROR)로 해석돼 **정상 응답 50건을 통째로 오류 처리** | 성공 응답에 resultCode 를 실어 보내는 모드 |
| 2 | 🔴 호출 폭주 — `page_size=1, max_records=1000` 이 **499회 요청** | 무작위 파라미터 200회 반복 |
| 3 | 🔴 `fetched`/`returned` 혼동 — contains 필터 결과를 fetched 에 덮어써 절단량을 오도 | 경고문 정합성 검사 |
| 4 | 🔴 출력 경로 이탈 — `name="../escaped"` 가 out_dir **밖에** 파일 생성 | 경로 주입 시도 |

수정 후 2차 라운드(극단 파라미터·유니코드 검색어·20스레드 동시호출·결정성 50회·실제 파일 왕복)
포함 **2,192건 전부 통과**. 회귀 테스트 38건 추가.

> 교훈: `_call` 을 monkeypatch 하는 테스트는 **전송·인코딩·재시도 계층을 건너뛴다.**
> 실제 HTTP 왕복을 태우는 하네스가 있어야 이 층의 결함이 드러난다.

### 2부: 접속 복구 → 라이브 실측 (약 150회 호출)
프로브 실행 중 `www.nl.go.kr` 접속이 복구됐다(기준 호출 total=63 이 c2_log 와 일치).
`scripts/probe_api.py` 를 새로 만들어 미검증 항목을 전수 확정했다.

**확정된 사실**

| 항목 | 결과 |
|---|---|
| `srchTarget` 지원 | `title`·`author`·`publisher`·`keyword`·`total` |
| `srchTarget` 폴백 | `isbn`·`classNo`·`callNo`·`subject`·오타 → **조용히 전 필드 검색** |
| `category` | 서버가 오류 013 에 **유효 목록을 실어 준다**. '전체' 는 거부. 자료구분별 합 = 전체(382=382) |
| 검색 의미론 | 토큰 매칭 + 적합도 정렬. **오탐 52%** |
| **큰따옴표 구문검색** | ✅ 동작 — `"교육불평등"` 28건, **오탐 0%** |
| AND/OR/NOT | ✗ 연산자 아님(`kwd=AND` 단독 검색 451,670건) |
| **`pageSize` 상한** | **500**(1000 거부) — 초판 100 → 상한까지 5회가 **1회**로 |
| 500 상한 기준 | **레코드 오프셋**(pageSize 10→51p, 100→6p, 둘 다 500건) |
| 서버측 연도 필터 | ✗ 부재(11개 후보 전부 무시) |
| `sort` | ✗ 부재(4개 키 × 7개 값 전부 순서 불변) |
| 0건 응답 | **`result` 키가 아예 없다** + `total:0` |
| 오류 봉투 | `{"errorCode":"011","errorMsg":"INVALID KEY:…"}` |
| 하이라이트 마크업 | `class="searching_txt"`, **토큰마다** span, 여러 필드에 실림 |

**라이브가 드러낸 추가 결함 2종**

- 🔴 **0건 응답을 오류로 처리하고 있었다.** `result` 키 부재를 ParseError 로 올렸는데, 이 API 는
  0건일 때 그 키를 뺀다. 검색어 오타·빈 분류 조회 등 **흔한 경우가 전부 오류로 죽던** 상태였다.
  → `total==0` 이면 빈 결과. 단 `total>0` 인데 `result` 가 없으면 레코드 누락이므로 오류 유지
  (적대적 하네스가 이 구멍을 지적해 규칙을 정밀화했다).
- 🔴 **`pageSize` 상한을 100 으로 오판**하고 있었다(수집 스크립트가 그 값을 썼을 뿐).

**내가 잘못 단정했다가 되돌린 것**
- `author`·`publisher` 를 "미지원, 폴백"으로 판정했으나 **오판**이었다. 주제어(`교육불평등`)로
  저자 검색을 해 0건이 나온 것을 미지원으로 읽은 것이다. 실제 저자명으로 재확인:
  `author=오욱환` 36 / `title=오욱환` 13 / `publisher=오욱환` 0 → 셋이 달라 각각 해석됨이 확정.
  ⚠️ **부재 증명에는 대조군이 필요하다** — "0건이 나왔다"는 미지원의 근거가 되지 못한다.
- 초판 문서의 "검색식에 OR 연산자가 없다"는 KCI 에서 검증된 사실을 **근거 없이 옮긴 것**이었다.
  정정했고, 이후 실측으로 (다른 근거에서) 사실임이 확인됐다.

### 6부: `exact` 기본값 검토 → **기본값 False 유지로 결론**

"오탐률 52%"를 근거로 exact 를 수집 기본값으로 올릴지 검토했다. **결과는 정반대였고,
내가 문서에 써둔 조언("정밀한 코퍼스가 필요하면 exact 를 쓸 것")이 틀렸음이 드러났다.**

문제는 '오탐률'이라는 지표 자체였다. 그것은 *제목에 검색어 문자열이 있는가* 를 잰 것이지
*주제가 무관한가* 를 잰 것이 아니다. 실제로 exact 가 무엇을 버리는지 확인했다.

| 검색어 | 기본 | exact | 재현율 손실 | 버린 것 중 구성어 모두 포함 |
|---|---:|---:|---:|---:|
| 교육형평성 | 31 | **5** | **84%** | 85% |
| 교육소외 | 84 | 25 | 70% | 88% |
| 디지털격차 | 46 | 18 | 61% | 96% |
| 교육불평등 | 63 | 28 | 56% | 71% |
| 학력격차 | 58 | 33 | 43% | 68% |
| 교육격차 | 244 | 168 | 31% | 61% |
| **합계** | **526** | **277** | **47%** | **76%** |

버려지는 것은 노이즈가 아니라 핵심 문헌이었다 — `교육형평성` 이 버린 표제 중
`학습자 중심 관점에서 본 교육의 형평성과 수월성 연구` · `OECD 국제지표로 본 한국교육의
형평성 분석` · `교육의 수월성과 형평성` 등.

**원인**: 한국어 복합어가 실제 표제에서 조사·수식어로 갈라진다(`교육의 형평성`,
`초중등교육의 형평성과`). 구문검색은 토큰 **인접**을 요구하므로 전부 탈락한다.
변형어를 `["교육형평성","교육 형평성","교육의 형평성"]` 로 늘려도 12건에 그쳐
기본 검색 31건에 못 미친다 — 변형어로 메울 수 있는 문제가 아니다.

**결정**: 기본값 `False` 유지. `exact` 의 용도는 전체 표제를 아는 특정 자료 조회·동명이의
구분·상한 검색어의 total 축소다. 코퍼스 수집은 기본 검색 + `contains` 후처리.
도구 설명·가이드·README 의 잘못된 조언을 전부 정정했고, 되돌아가지 않도록 회귀 테스트를 걸었다.

> 교훈: **대리 지표(proxy metric)를 결론으로 쓰지 말 것.** '제목에 문자열이 있는가'는
> 측정하기 쉬워서 골랐을 뿐 '관련 있는가'가 아니었다. 실제로 버려지는 레코드를 눈으로
> 확인하고서야 방향이 반대임을 알았다.

### 7부: v0.3.1 — 정정된 `exact` 안내를 배포본에 반영
6부의 정정은 소스에만 반영돼 있었다. **`.mcpb` 매니페스트의 도구 설명에는 옛 문구
`exact=true 로 구문검색(오탐 제거)` 가 그대로 남아 있었고**, 자체완결 바이너리는

- `nl_search` → "기본 검색은 토큰 매칭이며, exact(구문검색)는 재현율을 크게 낮추므로
  전체 표제를 아는 특정 자료 조회에만 사용"
- `nl_collect` → "⚠️ exact 는 재현율 손실이 커(평균 47%) 코퍼스 수집에는 부적합"

⚠️ 매니페스트를 JSON 로드→덤프로 고쳤더니 한 줄짜리 배열이 전부 펼쳐져 diff 가 78줄로
불었다. 내용은 같고 스키마도 통과했지만 **실제 변경이 묻힌다.** 되돌리고 문자열 치환으로
다시 해 실질 변경 3줄씩만 남겼다. 기계적 재포맷은 리뷰 가능성을 해친다.

| `manageName` | ✅ **완전분할**(본관 974 + 디지털 872 + 어린이 10 = 1,856 = 전체) |
| `licYn` | ✅ 동작하나 **손실 있음** |
| `kdcName1s` | ✅ 동작하나 사회과학에 쏠려(1,674/1,856) 효과 낮음 |
| 나머지 27개 | ✗ 무시 (kdcCode1s·classNo·typeCode·typeName·menuName·mediaName·placeInfo·docYn·isbn·controlNo·regDate·lang·univName·detailSearch·f1 …) |

⚠️ **이름만 보고 대칭을 가정하면 안 된다** — `kdcCode1s`(코드)는 무시되는데 `kdcName1s`(이름)는
동작하고, `licYn` 은 되는데 `docYn` 은 안 된다.

⚠️ `licYn` 의 손실을 **A~Z 전수 탐색**으로 확정했다. 교육복지/도서/본관 974건에서
D·F·L·N·S 다섯 값의 합이 472건에 그쳤다 — 나머지 502건은 licYn 이 비어 어떤 값으로도
선택할 수 없다. 처음엔 상위 500건만 관찰해 값 집합을 추정했는데, 그 관찰 자체가
**상한에 갇혀 편향**돼 있었다(`U` 값을 뒤늦게 발견).

**구현 — `search_partitioned_meta()`**
축을 순서대로 적용하며 상한에 걸린 조각만 다음 축으로 더 쪼갠다.
핵심 설계는 **부모 조각도 상한까지 받아 합집합에 넣는 것**이다. 그러면 `licYn` 처럼
불완전한 축을 써도 손해가 나지 않는다(합집합 ≥ 부모). 이 한 가지가 회복량을 크게 바꿨다 —
2차원 격자를 따로 계산했을 때는 48%였는데, 부모 합집합을 넣으니 67%가 됐다.

| 깊이 | 축 | 회수 | 비율 | 요청 |
|---:|---|---:|---:|---:|
| — | 분할 없음 | 500 | 7% | 1 |
| 1 | `category` | 2,134 | 30% | 13 |
| 2 | `+manageName` (기본) | 3,265 | 46% | 25 |
| 3 | `+licYn` | **4,722** | **67%** | 60 |

`nl_collect(auto_partition=True, partition_depth=1~3)` 로 노출. 전수는 여전히 불가능하며
깊이 3에서도 33%가 남는다 — `unreachable`·`still_capped` 로 보고한다.

**테스트 가짜 서버를 모집단 기반으로 재작성** — 처음엔 셀마다 id 공간을 분리했는데,
그러면 부모와 자식이 다른 레코드가 되어 **합집합이 root 를 초과**하는 비현실적 결과가 나왔다
(깊이3에서 8,151 > 7,028). 고정 모집단을 만들어 질의마다 거르는 방식으로 바꾸니
실측을 거의 그대로 재현한다(깊이1 30%↔30% · 깊이2 47%↔46% · 깊이3 73%↔67%).
회귀 8건 추가(143 → 151).

### 실측이 아니었으면 틀렸을 것 3가지
1. **`docYn`·`licYn` 은 불리언이 아니다.** 이름이 `…Yn` 이라 Y/N 으로 읽히지만 실제는 열거코드
   (`NL_VIEWER`·`LD_VIEWER`·`FILE`·`LINK`·`N` / `L`·`F`·`S`·`D`·`N`·`Y`).
   실측 1,124건에 `docYn="Y"` 는 **한 건도 없다** — `== "Y"` 로 판정했으면 전건 오판이었다.
   (KCI 의 `pubi-year`·`isseue` 오타 사례와 같은 종류의 함정이다.)
2. **`pubYearInfo` 형식이 하나가 아니다.** 4자리 703 · 6자리 186 · 8자리 168 · 9~14자리 8
   (`2019 (2020 9쇄)` 같은 값) · 빈값 59. 정수 변환이나 단순 앞 4자 절단은 조용히 깨진다.
3. **`controlNo` 는 31.0% 가 빈다.** 온라인자료(`typeCode=D1`)엔 KOLIS 제어번호가 없다.
   반면 `id` 는 **전건 존재** → 중복제거 1차 키는 `id` 여야 한다.

### 🔴 500건 상한 — 이 API 의 지배적 제약
- 공식 오류코드 **`012 DATA LIMIT 500`** (v0.1.0 이 남긴 서지정보 가이드에 기재돼 있었다)
- 실측 확증: `c2_log.txt` 의 `교육복지: total=1856 수집=500 ⚠절단`.
  수집 스크립트는 30페이지(3,000건)까지 허용했으나 6페이지째부터 빈 배열이 왔다.

**질문: 페이지네이션으로 해결되는가 → 안 된다.** 상한이 오프셋에 걸려 있어 같은 검색식으로는
501번째에 도달할 수 없다. `pageSize` 를 키우거나 페이지를 나눠도 동일하다.

**해결은 검색 공간 분할이다** — 각 조각의 `total` 이 500 미만이 되게 만든다.
검색어 세분화(✅ `nl_collect(terms=[…])`) · `category` 분할(✅) ·
`sort` 뒤집기(❓ 미검증) · 연도/KDC 서버측 필터(❓ 파라미터 지원 미확인).

⚠️ **함정**: `year_from`/`contains` 는 **로컬 후처리**라 상한을 풀어주지 않는다.
회귀 테스트 `test_연도필터는_로컬후처리라_상한을_풀어주지_않는다` 로 이 성질을 고정했다.
